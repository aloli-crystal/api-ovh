== 0.4.2 (29 avril 2026)

=== Modifié

* **Repo GitHub renommé** `aloli-crystal/crystal-api-ovh` →
  `aloli-crystal/api-ovh` (convention de nommage Aloli : les créations
  originales abandonnent le préfixe `crystal-`). Les anciens liens
  redirigent automatiquement.
* Champ `name:` du `shard.yml` mis à jour de `ovh-api` à `api-ovh`
  (alignement avec le nom du repo). Le module reste `OvhApi`
  (sémantiquement plus naturel).
* Nouveau fichier d'entrée shim `src/api-ovh.cr` (charge
  `src/ovh_api.cr`) ; `require "ovh-api"` devient `require "api-ovh"`.

== 0.2.4 (21 avril 2026)

=== Ajouté

* `client.dedicated_servers.boot_from_disk(service_name)` : orchestration
  inverse de `prepare_rescue`. Trouve le `bootId` de type `harddisk`,
  l'arme via `set_boot`, puis déclenche un reboot. À utiliser après une
  install réussie pour que le serveur redémarre sur l'OS fraîchement
  posé au lieu de retomber en rescue.

== 0.2.3 (20 avril 2026)

=== Corrigé

* `prepare_rescue` : sur les serveurs OVH qui exposent plusieurs profils
  `bootType == "rescue"` (cas typique : un `ipxe-shell` + un
  `rescue12-customer`), on prenait le premier retourné par l'API — souvent
  l'iPXE shell, inexploitable comme OS (simple shell iPXE interactif, ni
  SSH ni apt). Résultat : après reboot le serveur n'est jamais joignable,
  le monitoring OVH escalade vers une intervention.
+
Correction : `find_rescue_boot_id` filtre désormais sur les kernels
`rescue*` (Debian rescue : `rescue12-customer`, `rescue64-pro`…) et écarte
les profils `ipxe-shell`. Nouveau prédicat `Boot#linux_rescue?` pour
exposer la règle côté API publique.

=== Ajouté

* `Boot#linux_rescue?` : distingue un rescue Debian utilisable d'un
  `ipxe-shell` (les deux portent `boot_type == "rescue"` côté OVH).
* Spec couvrant le cas loulou (bootIds 203323 ipxe-shell + 230242
  rescue12-customer) : vérifie qu'on prend bien le 230242.

== 0.2.2 (20 avril 2026)

=== Corrigé

* `prepare_rescue` : le champ OVH `rescueSshKey` attend la **clé publique
  brute** (`ssh-ed25519 AAAA... user@host`), pas le nom de la clé. La
  doc OVH indique pourtant « name of the ssh key », ce qui est trompeur
  — l'API renvoie `400 {"message":"SSH key is not valid"}` quand on
  passe le nom. Vérifié en consultant `GET /dedicated/server/{serviceName}` :
  le champ `rescueSshKey` du serveur y est stocké en contenu brut.
+
`prepare_rescue` fait désormais un `GET /me/sshKey/{name}` pour
récupérer le contenu avant de le passer à `set_boot`. L'API
publique est inchangée (on passe toujours le nom en argument) :
compatibilité ascendante côté appelants.

=== Ajouté

* Spec étoffé : couvre le lookup intermédiaire `ssh_keys.get` + assertion
  que le `PUT` envoie la clé brute, pas le nom.

== 0.2.1 (20 avril 2026)

=== Corrigé

* `prepare_rescue` : l'appel `POST /dedicated/server/{serviceName}/netbootOption`
  n'existe pas côté OVH (renvoie HTTP 404 « Got an invalid (or empty)
  URL »). La bonne approche est de passer `rescueSshKey` dans le corps
  JSON du `PUT /dedicated/server/{serviceName}`, dans la même requête
  que `bootId`. Corrigé : `set_boot` accepte maintenant un paramètre
  optionnel `rescue_ssh_key`, `prepare_rescue` fait une seule requête
  PUT au lieu de deux (PUT + POST raté).

=== Retiré

* `client.dedicated_servers.set_netboot_option(...)` : méthode retirée
  (l'endpoint n'existait pas). La fonctionnalité est intégrée dans
  `set_boot(service_name, boot_id, rescue_ssh_key: ...)`.

=== Modifié

* `set_boot` : nouveaux paramètres optionnels `rescue_ssh_key : String?`
  et `rescue_mail : String?`, ajoutés au corps du PUT quand non-nil.
  Rétrocompatible : `set_boot(service_name, boot_id)` continue de
  fonctionner à l'identique.

== 0.2.0 (20 avril 2026)

=== Ajouté

* `client.dedicated_servers.boots(service_name)` : liste des bootId dispo.
* `client.dedicated_servers.boot(service_name, boot_id)` : détail d'un boot, struct `OvhApi::Boot`.

==== Fondations du projet

* Squelette initial (`shard.yml`, `LICENSE` MIT, README bilingue FR/EN).
* Convention Aloli : branche par défaut `production`, messages de commit
  en français, licence MIT, auteurs `ALOLI sas`.

==== Cœur du client

* `OvhApi::Client` : signature `X-Ovh-Signature` locale (SHA-1 hex préfixé
  par `$1$`), calculée sur `secret+ck+method+url+body+timestamp`.
* Synchronisation d'horloge via `/auth/time` (mémorisation d'un offset,
  évite de re-interroger à chaque appel).
* Routage multi-endpoint : `:eu` (défaut), `:ca`, `:us`, Kimsufi EU/CA,
  SoYouStart EU/CA. L'argument accepte aussi une URL complète.
* Transport HTTP abstrait `OvhApi::HttpTransport` avec implémentation
  `DefaultHttpTransport` (stdlib `HTTP::Client`), permet l'injection d'un
  double en test.

==== Endpoints de provisioning

* *SSH keys* (`/me/sshKey`) : `list`, `get`, `create(name, key, default)`,
  `delete`.
* *Dedicated servers* (`/dedicated/server`) : `list`, `info`, `reinstall`
  (endpoint moderne 2024 avec `operatingSystem` + `customizations`),
  `installation_templates`, `tasks` (avec filtres `function`/`status`),
  `task` (détail individuel).
* *Reverse DNS* (`/ip/{ip}/reverse`) : `list`, `get_reverse`, `set_reverse`,
  `delete_reverse`.

==== Taxonomie d'erreurs

* `OvhApi::Error` (base).
* `AuthenticationError` (HTTP 401/403).
* `NotFound` (HTTP 404).
* `RateLimited` (HTTP 429, expose `retry_after`).
* `ApiError` (autres, expose `http_status` et `error_code`).

==== Tests et exemples

* Specs Crystal avec `FakeTransport` pur stdlib (aucun appel réseau) :
  signature, offset d'horloge, en-têtes, corps JSON, query string,
  gestion d'erreurs, sérialisation des `Task` et `Reverse`.
* Vecteur de signature déterministe recalculé à la main dans les specs.
* Exemple exécutable `examples/provision_debian.cr` : installation Debian 12
  + polling de tâche + pose de reverse DNS, avec garde-fou `OVH_CONFIRM=yes`.

==== Intégration continue

* CI GitHub Actions : format Crystal + specs sur Linux et FreeBSD 15
  via `cross-platform-actions/action`, avec compilation de l'exemple
  (`mkdir -p bin && crystal build ...`).
