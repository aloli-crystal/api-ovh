= api-ovh — Architecture
:toc: left
:toc-title: Table des matières
:toclevels: 3
:source-highlighter: rouge

Ce document décrit la signature OVHcloud, le routage multi-endpoint et la
taxonomie d'erreurs exposée par ce shard.

== Périmètre

[cols="1,3"]
|===
| api-ovh fait | api-ovh ne fait pas

| Calcul local de la signature `X-Ovh-Signature`.
| OAuth 2.0 applicatif (pas supporté par l'API v1).

| Synchronisation d'horloge via `/auth/time` (une fois par process).
| Cache distribué d'offset entre plusieurs process.

| Transport HTTP abstrait, injectable, stdlib par défaut.
| Client HTTP asynchrone à la place de `HTTP::Client`.

| Taxonomie d'erreurs fine (401 / 404 / 429 / autres).
| Backoff automatique sur 429 (l'appelant gère `retry_after`).
|===

== Décisions clés

=== ADR-001 — Pure stdlib Crystal (Accepted)

*Contexte.* Le shard vise une intégration dans beryl, qui est
déjà en pure stdlib. Ajouter une dépendance (crest, halite…) démultiplierait
la surface de maintenance.

*Décision.* api-ovh n'utilise que `HTTP::Client`, `OpenSSL`/`Digest::SHA1`,
`JSON` et `URI` de la stdlib. Aucun `dependencies:` dans `shard.yml`.

*Conséquences.* Pas de `WebMock` non plus : les tests utilisent un
`FakeTransport` maison, plus simple et explicite (cf. ADR-004).

=== ADR-002 — Schéma de signature X-Ovh-Signature (Accepted)

*Contexte.* L'API v1 OVH impose ce schéma : quatre en-têtes
(`X-Ovh-Application`, `X-Ovh-Consumer`, `X-Ovh-Timestamp`, `X-Ovh-Signature`)
où la signature est un SHA-1 hex préfixé par `$1$`.

*Décision.* Implémentation littérale du schéma, calculée sur :

----
"$1$" + SHA1_HEX( application_secret + "+" +
                  consumer_key       + "+" +
                  HTTP_METHOD        + "+" +
                  FULL_URL           + "+" +
                  BODY_STRING        + "+" +
                  TIMESTAMP )
----

Le `FULL_URL` *inclut* la query string (après l'éventuel `?`). Le
`BODY_STRING` est le corps JSON compact *exact* envoyé (pas de re-sérialisation
intermédiaire, sinon la signature diverge).

*Vecteur de test.* `secret=appsecret, ck=ck, method=GET,
url=https://eu.api.ovh.com/1.0/me, body="", ts=1700000000` doit produire
`"$1$" + SHA1_HEX("appsecret+ck+GET+https://eu.api.ovh.com/1.0/me++1700000000")`.
Voir `spec/ovh_api/client_spec.cr`.

=== ADR-003 — Offset d'horloge mémorisé (Accepted)

*Contexte.* OVH accepte un écart de 30 secondes entre `X-Ovh-Timestamp` et
l'heure serveur. Si l'horloge locale dérive, toutes les requêtes sont
rejetées avec `INVALID_SIGNATURE`.

*Décision.* À la première requête signée, api-ovh interroge `/1.0/auth/time`
(endpoint non signé) et calcule `delta = time_ovh - time_local`. Les appels
suivants utilisent `Time.utc.to_unix + delta` sans nouvel aller-retour.

*Conséquences.* Un process long-running résilient à une dérive de NTP (la
dérive est figée au démarrage). Si elle pose problème, l'appelant peut
réinitialiser `client.time_delta = nil`.

=== ADR-004 — Transport HTTP abstrait (Accepted)

*Contexte.* Pour tester la signature et la gestion d'erreurs sans appel
réseau, et sans WebMock, il faut intercepter la couche HTTP.

*Décision.* Classe abstraite `OvhApi::HttpTransport` avec une seule méthode
`#request(method, url, headers, body) : {Int32, String}`. Deux
implémentations : `DefaultHttpTransport` (stdlib `HTTP::Client`) et
`FakeTransport` (dans `spec_helper.cr`, enregistre les requêtes et renvoie
des stubs prédéfinis).

*Conséquences.* Les specs sont déterministes, sans flakiness réseau, et
exécutent le code de signature réel. Le coût est minime : une interface et
une classe de stub.

=== ADR-005 — Taxonomie d'erreurs (Accepted)

*Contexte.* OVH renvoie différents codes HTTP avec des sémantiques variées.
Laisser remonter une `Exception` générique force l'appelant à parser le
message.

*Décision.*

[cols="1,1,3"]
|===
| HTTP | Classe | Sens

| 401, 403 | `AuthenticationError` | Clé/consumer invalide, signature rejetée, scope manquant.
| 404      | `NotFound`            | Ressource absente (service, IP, clé SSH, tâche).
| 429      | `RateLimited`         | Quota dépassé. Expose `#retry_after` (secondes).
| 5xx / autres | `ApiError`        | Expose `#http_status` et `#error_code` (champ `errorCode` / `class` du corps).
|===

Toutes héritent de `OvhApi::Error`, ce qui permet un `rescue` global.

=== ADR-006 — Endpoint moderne pour la réinstallation (Accepted)

*Contexte.* OVH a deux endpoints historiques :

* `/dedicated/server/{serviceName}/install/start` — schéma 2015, paramètres
  plats (`templateName`, `details` avec sous-champs).
* `/dedicated/server/{serviceName}/reinstall` — schéma 2024, paramètres
  structurés (`operatingSystem`, `customizations`, `storage`).

Le schéma moderne couvre les serveurs gamme récente (Scale, Advance, High
Grade, Kimsufi 2024+). Certains serveurs legacy ne sont supportés que par
`install/start`.

*Décision.* Par défaut, `#reinstall` appelle l'endpoint moderne. Le
paramètre `extra:` permet d'ajouter des champs libres. Un fallback explicite
vers `install/start` sera ajouté en v0.2 si un utilisateur rencontre un
serveur rejeté par `reinstall`.

== Flux de réinstallation

. `client.ssh_keys.list` → vérifier que la clé cible existe (faute de quoi
  le `customizations.sshKey` est rejeté).
. `client.dedicated_servers.installation_templates` → vérifier le template.
. `client.dedicated_servers.reinstall(...)` → crée une `Task`.
. Polling de `client.dedicated_servers.task(...)` toutes les 30 s jusqu'à
  `task.done?`.
. `client.ips.set_reverse(ip:, reverse: "hostname.")` → DNS inverse.

Un cycle install + reverse dure typiquement 20 à 60 minutes côté OVH.

== Flux rescue mode (v0.2)

La bascule en rescue pour du diagnostic ou de la réparation suit une
logique différente de la réinstallation : pas de template à choisir,
mais un *bootId* à sélectionner parmi la liste exposée par le serveur.

. `client.dedicated_servers.boots(service_name)` → `[1, 2, 42, …]`.
. Pour chaque `bootId`, `client.dedicated_servers.boot(service_name, id)` →
  `bootType` (`harddisk`, `rescue`, `ipxeCustomerScript`, `network`,
  `power`), `kernel` (`rescue64-pro`, …), `supportsUEFI`.
. Retenir le premier `bootType == "rescue"` dont `supportsUEFI` est
  absent ou vaut `yes` / `both` / `only`.
. `set_boot(service_name, rescue_id, rescue_ssh_key: ssh_key_name)` →
  un seul `PUT /dedicated/server/{serviceName}` qui arme le netboot *et*
  déclare la clé à injecter. OVH injectera cette clé dans
  `/root/.ssh/authorized_keys` du rescue au démarrage.
. `reboot(service_name)` → `Task` (`function=hardReboot`).

Les `bootId` *varient selon la gamme et le serveur* : un Advance-1 et
un Scale-3 n'exposent pas les mêmes identifiants. Les coder en dur
casserait à chaque nouvelle gamme OVH. Le helper
`prepare_rescue(service_name, ssh_key_name)` encapsule les étapes ;
l'appelant n'a plus qu'à poller la `Task` retournée.

Le champ `supportsUEFI` peut être absent sur les profils bas niveau
(`power`, anciens `network`). `Boot#uefi_compatible?` considère alors
que la question ne se pose pas et renvoie `true` — sinon on
exclurait à tort les serveurs antérieurs à UEFI et les profils qui
ne pilotent que l'alim.

=== Envisagé (pas d'engagement de date)

==== Modules typés candidats

Critère : un endpoint est candidat à un module typé si (a) il est
fréquemment utilisé dans les workflows Aloli, (b) son schéma est
stable côté OVH, (c) la valeur ajoutée du typage justifie le coût de
maintenance face aux évolutions de schéma. Sinon, `raw_*` reste la
voie recommandée.

* `client.me.credentials` — listing, expiration, révocation des
  consumer keys. Pertinent ISO 27001 A.5.17 (rotation des credentials).
* `client.me.api_logs` — extraction du journal d'appels API. Pertinent
  ISO 27001 A.8.15/A.8.16 (logging + monitoring).
* `client.me.identity` — IAM OVH (utilisateurs, groupes, rôles).
  Pertinent ISO 27001 A.5.15/A.5.16.
* `client.me.access_restriction` — IP allow-list, MFA TOTP/U2F.
  Pertinent ISO 27001 A.8.5.
* `client.secret` — OVH KMS (clés chiffrées). Pertinent ISO 27001 A.8.24.
* `client.ssl` — certificats X.509. Pertinent ISO 27001 A.8.24.
* `client.services` — inventaire global des actifs OVH attribués.
  Pertinent ISO 27001 A.5.9.

==== Améliorations transverses

* `/order/cart` — commander un nouveau serveur depuis zéro.
* Fallback `install/start` pour les serveurs dédiés legacy non
  supportés par `/reinstall`.
* Backoff automatique configurable sur 429 (`retry: true` / `retry: 3`
  sur `call`), respectant `retry_after`.
* Support `?extras` sur `/dedicated/installationTemplate` pour les
  partitions personnalisées.

=== Hors-périmètre durable

* OAuth 2.0 applicatif — l'API v1 ne le supporte pas, le schéma
  API Keys + consumer key reste la voie officielle.
* Streaming WebSocket / Server-Sent Events — l'API v1 OVH n'expose
  pas de canal temps réel ; le polling reste la norme.
* Async-first (`HTTP::Client` non-bloquant via fibers seulement) — le
  `Client` actuel est bloquant. Concurrence côté appelant via
  `spawn` / `Channel`.
